## 四、Q4 · 能不能做标杆 + 怎么变现

### 4.1 为什么「AI 可见度监测」这条路走不通

不是投入不够，是**三条同时卡死**：

1. **功能差 4–7 项**，且缺的那项（真实引擎查询）是**赛道定义性功能**——没有它，产品在分类上就不属于这个品类。
2. **数据差 3 个数量级**：Ahrefs 509M prompts、Semrush 317M+，历史回溯到 2024-08。个人站无法追。
3. **境内结构性不可达**（S1）：真调境外引擎 + 中文镜像，对境内用户是内在冲突。

### 4.2 但有一个位置是空的，而且只有我们能占

**诊断层** —— 有观察指出 Otterly 与 AthenaHQ：

> *"both tell you, in clean detail, **where you appear** in AI answers, and **neither reliably steps you through why a model skips you or what to change on your site to fix it**."*

全赛道挤在「你在哪出现」，「为什么不被引用、该改什么」是普遍缺口。

**但必须诚实加两条限制**：
- **不是没人在做**：SearchScore（£950/£1,500）、Otterly（16 类 recommendations）、Peec、Rankscale 都在往执行层走。区别是**它们做成咨询/建议，我们做的是可自动化诊断**。
- **我们目前也没真占住**：完整诊断需要「站点信号」+「引擎回答」**两侧数据，我们只有一侧**。

⇒ 准确表述是：**「用站点侧信号把别人只做咨询的执行层产品化」**，不是「从零开辟诊断层」。

### 4.3 支撑这个位置的最强资产：324 站点数据

首页埋着的原始统计（仅 3.6% robots.txt 拦 AI 爬虫、AI guidance 均值 20%、structured data 12%、
discovery endpoints 1%、E-E-A-T 32%）是**全赛道最可能被行业引用的数字**——
它回答了一个所有人都在问、没人有数据回答的问题。

**但它现在只是首页一个段落**：没有独立页面、没有方法论、无法引用、无法更新。

**窗口期**：GeoReady 做过同类基准（2100+ 站点，有日期标注与样本偏差声明），
但 **https://geoready.dev/benchmark 返回 404** ⇒ **有人做了但没做完**，我们的机会在「做对」不在「抢先」。

### 4.6 🔴 前置硬约束：付费档能力 < 免费档能力（倒挂）

两条实测：

- **自托管 CLI/MCP 用户可自行更换 LLM 端点**（`LLM_URL` + `env.TOKENRHYTHM_API_KEY`）
- **Pro 档 `worker/pro.js` 没有 API key 体系**

⇒ **免费的那个版本比付费的更开放。**

| 路径 | 影响 |
|---|---|
| **A · 订阅深耕** | 🔴 **直接被杀死** —— 软件能力免费可得，凭什么付费 |
| **B · 服务先行** | ✅ **反而被强化** —— 软件不值钱，唯一卖钱的是「人工落地 + 复检」 |
| **C · B2B2B 白标** | 🟡 部分受影响（白标买家买的是品牌化交付，不是 API） |

⇒ **这是「为什么只能选 B」最硬的一条论证**，比「流量差 135–170 倍」更本质：
那个是量的问题，这个是**商业模式是否成立**的问题。

**修法**：Pro 档补 API key 体系（按提问量配额），让付费档在「可编程 + 配额」上
**严格强于**免费自托管。这一条应排进路线图 P0，否则分层做出来也卖不动。

## 十二、自建 vs 集成：成本估算（决定「真调引擎」要不要做）

**工作量模型**：1 sample = 1 prompt × 1 引擎 × 1 次；Pro 档默认 5 prompts × 4 引擎 × 1 次/天 × 30 天
= **600 samples / 用户 / 月**

| | 路线 A：真实 web 界面自动化 | 路线 B：LLM API + web search |
|---|---|---|
| 前置固定投入 | **16–25 人日** | **7–12 人日** |
| 单用户月边际成本 | **≈$0.9**（+ 固定 **$80–280/月**） | **≈$4.8–7.8**（中位 $6.0） |
| 持续维护 | 0.5–1 人日/月 | 0.2 人日/月 |
| 证据强度 | 真实消费界面 = 硬证据 | 真检索，但非目标引擎排序逻辑 |

**实测单价（非估算）**：Perplexity web_search **$0.0025/次**（官方 worked example 单请求总成本 $0.0059）
· OpenAI web search **$10.00/1k calls** · **Cloudflare Browser Rendering：Free 10 浏览器小时/月**，超出 $0.09/小时
（**我们已在 CF 上，不需要新增供应商**）

**盈亏平衡**：运营成本交叉点 **39 个付费用户**；12 个月回本需 **72 个持续付费用户**
（若单次耗时 180s 则需 **111 个**）

⇒ **结论：路线 A 现在做是坏账，不做。**

⚠️ **但注意一个反直觉的点**：路线 B 相对**现状**仍是巨大升级。
现状是 deepseek + 4 个人格 prompt **扮演** 4 个引擎、**零检索**（代码自认 "a simulation"）；
路线 B 是「从零检索到真检索」的最小可行升级——**是三档里唯一既不改变成本结构、又能摘掉 "simulation" 帽子的选项**。

### ⚠️ 两个必须一并解决的隐患（开源路发现，我此前完全没意识到）

1. **随机公共 CORS 代理不可靠、不可观测** —— 目标站封禁与失败率无从监控。
2. **客户 URL 明文发给 allorigins / codetabs 等第三方**
   ⇒ 与 `privacy.astro`「URL 不上传」**现在是冲突的，不是未来才冲突**。

⇒ 这修正了变现路 §13.2 的判断：那条原来被标为「未来冲突（加真实查询后）」，
**实际是「现存问题」——因为公共 CORS 代理抓取本身就已经把 URL 交给第三方了**。

### 一个必须由你拍板的口径问题

检查项数量当前**三种写法并存**：

| 说法 | 出处 | 状态 |
|---|---|---|
| **85** | `scoring.js` 权威定义（11 维内） | ✅ 真实 |
| **99** | 代码实测总数（85 + 负面信号 8 + 提示词注入 6） | ✅ 真实，但把扣分项算进「检查项」 |
| **“85+”** | 对外文案 | ⚠️ 实际正好 85，**加号是虚增** |

**我的推荐：对外统一为「99 checks across 11 dimensions」。**
理由：① 99 是访客真正得到的检查总量，可验证；② “85+” 的加号是虚增，与产品的诚实定位直接冲突；
③ 11 维与 `scoring.js` 对齐，杜绝再次出现「11 vs 14」这类乌龙。

若你更看重「评分项」与「扣分项」的区分，次选是：
「85 scoring checks across 11 dimensions, plus 14 penalty checks」。
